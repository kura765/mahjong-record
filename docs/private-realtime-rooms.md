# 非公開リアルタイム共有ルーム — 開発設計（v3.0）

## 原則
- 本番サイト（`main`）とバックアップ（`backup/v2.9-stable`）は、開発中に変更しない。
- 既存のローカル対局データ（`localStorage` の `mahjongPrototypeV1`）は移行・削除・上書きしない。
- 開発用データベースと本番用データベースを分離する。最初は架空のテスト記録のみ利用する。
- 共有ルームは招待された人だけが閲覧できる。部屋の作成者だけが編集できる。
- 「画面上の編集ボタン非表示」だけでなく、データベース側の権限検査で書き込みを拒否する。

## ユーザー体験
1. 作成者がログインし、「共有ルームを作る」を実行。
2. 作成者が半荘名・対局日・参加者・東南西北を設定。
3. 参加者は招待リンクを開いて、閲覧資格の確認を受けてから入室。
4. 作成者が局を確定すると、閲覧者側の点数・本場・供託・局履歴を自動更新。
5. 観戦者は閲覧のみ。開始、局編集、終了、無効化などは不可。
6. 通信が切れたら再接続し、権限を確認して最新の状態を再取得。

## データモデル案
- rooms: id(UUID), owner_user_id, title, match_date, created_at, status
- room_members: room_id, user_id, role(owner/viewer), joined_at
- invitations: room_id, token_hash, expires_at, revoked_at（平文トークンはデータベースに保存しない）
- room_snapshots: room_id, revision, payload(JSON), updated_at, updated_by
- room_events: room_id, revision, action_type, action_payload, created_at

## 最低限の権限制御（サーバー側）
- ルームの読み取り：owner、または有効な参加権限を持つuser_idのみ。
- ルームの更新：認証済みownerのみ。roleの自己昇格は禁止。
- 招待の発行・失効：ownerのみ。
- 招待リンクの保持だけでログイン済みユーザーのアクセス制御を無条件に迂回しない。
- Realtime配信もルームごとの許可に基づく。URLを推測するだけで入室不可。
- 一度失効した招待リンク／権限のアクセスは遮断する。

## 更新整合性
- 作成者だけが更新できる設計を採用する。
- revisionを更新する際、直前のrevisionが一致することを確認する（旧状態への上書きを防止）。
- 二重送信には同一操作IDで冪等に応答する。
- 変更が承認された後に購読者へ通知する。閲覧者は再接続時にサーバーの最新値を再取得。

## 現行版との分離
- `main` のGitHub Pagesは従来の固定URLを使い続ける。
- 開発ブランチの作成だけではGitHub Pagesの別URLは自動的に生まれない。
- 実際の試験サイトは別のデプロイ先、別リポジトリ、または独立パスで構築する必要がある。
- GitHub Pages上のフロントエンドコードは公開されるため、サーバー秘密鍵を埋め込まない。
- 開発開始前に現在の「バックアップを書き出す」でJSONを保存する。
