# 開発用 Supabase 環境の準備

## いま用意できているもの
- `supabase/migrations/20261121_private_rooms_initial.sql`: 非公開ルーム、閲覧メンバー、共有スナップショットの試作DBスキーマ
- **未適用**: Supabaseの実プロジェクトにSQLを実行していません
- ブランチ: `feature/private-realtime-rooms` のみ。本番`main`、復元用`backup/v2.9-stable`は無変更

## 使い方（まだ外部サービスの操作が必要）
1. Supabaseで**開発専用**プロジェクトを作成する（本番用と分ける）。
2. Auth設定で作成者の認証方式を選ぶ。初期案はメール認証。参加者の招待方法は後続工程で設計。
3. SQL Editorで上記のmigrationを開発プロジェクトに限って実行する。**まだ実施を推奨しない**：下記の未完了事項を先に実装・検証する。
4. SQLはリポジトリ上では公開される設計情報。パスワードやservice_role/secret keysは絶対にコミットしない。

## 制約と今後の実装
- 上記のDBテーブルはアプリUIとまだ接続されていない。部屋の作成・招待・入室・リアルタイム更新は未実装。
- 認可は画面側だけでなく、RLSで書込をownerに限定する設計。
- 現時点のDBポリシーは、開発中にownerが参加者IDを追加するところまで。一般ユーザー向け招待フローは後続の安全なRPCと検証を待つ。
- owner更新とrevisionの原子性が不足しているため、現状を本番共有には使わない。
- Realtime通知はRLSのテスト成功後に有効化する。
- 本番の端末データは引き続きローカル（`mahjongPrototypeV1`）。自動移行はしない。
- 招待トークンの発行・失効と端末変更に対応する認証方法は次の工程で具体化する。
