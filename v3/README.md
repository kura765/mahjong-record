# 麻雀対局記録サイト v3.0 — クラウド試験版

**既存の `index.html`（v2.22）は変更しません。** これは段階的な開発用機能です。

## ファイル

- `v3/cloud.html`：クラウド接続・メールログイン・ルーム作成・招待・スナップショット読込/書出し
- `supabase/v3_schema.sql`：非公開ルーム、RLS、権限付きRPC、24時間/1回限り招待、版番号管理
- `v3/migration-check.html`：既存バックアップの形式検査
- `v3/import-preview.html`：ローカルJSONバックアップ間の衝突検査と統合

## Supabase の初期設定（プロジェクト所有者）

1. Supabaseの新規プロジェクトを準備する（既存の本番DBにいきなり適用しない）。
2. SQL Editor で `supabase/v3_schema.sql` を実行する。失敗した場合はメッセージを確認し、再実行を繰り返す前に原因を解決する。
3. Authentication > Providers で Email のOTP/マジックリンクを有効にする。送信制限を確認する。
4. Authentication > URL Configuration で実際のクラウド試験版URLを Redirect URLs に追加する（例：`https://kura765.github.io/mahjong-record/v3/cloud.html`）。
5. Supabase の Project URL と **Publishable key（または anon key）** をクラウド試験画面に入力する。**service_role や secret key は絶対に使用しない。**
6. 2つの別アカウントで作成者と閲覧者の権限を検証する。招待リンクは1回使用すると再利用できない。
7. この段階では Supabase Realtime publication は設定しない。ルーム一覧更新は手動。

## クラウドに保存するデータ

`mahjong_room_matches` は `room_id` と `match_key` を複合キーとし、JSONBの `payload` に `{kind,match}` を記録します。kind は `completed` / `suspended` / `active` です。各更新は `mahjong_save_match` RPC経由のみ許可され、版番号の競合をチェックし、履歴テーブルに記録します。

招待トークンは64文字のランダムな16進文字列で、DBにはSHA-256ハッシュのみ保存します。招待は作成から24時間有効・使用は1回限り。メンバーは閲覧専用です。

## 既知の未実装事項と注意

- **Supabaseプロジェクトの作成・SQL実行はまだ未実施**。GitHubにファイルを登録した段階です。
- クラウドへの自動同期、Realtimeによる他端末への自動反映、既存v2.22の対局入力UI統合は未実装。
- バックアップ取り込みはメタデータと最大500半荘を1つのRPCトランザクションとして保存します。既存と完全一致するものは省略し、半荘または設定情報が異なる場合は全件ロールバックします。応答受信前にネットワークが切れた場合は結果が不明なため、再度同じバックアップを選択してください（成功済みレコードは重複せず省略します）。
- 既存のクラウド側に同IDかつ異なる内容の半荘があれば上書きを拒否します。
- クラウド試験画面のJSON書き出しはルームの保存済みスナップショット形式であり、v2.22の全体バックアップとは異なります。そのままv2.22の「バックアップ読み込み」には渡さないでください。
- 作成者しか更新できない仕組みです。参加者の閲覧専用制約はDB側のRLSとRPCで実装しています。公開利用前に権限/招待/データ移行の実機テストが必要です。
- ローカルストレージの設定保存は公開用のSupabase URL/キーのみ。個人のservice_role/secret keyを記録しないでください。

## クラウド一括取り込みの確認項目（Supabase接続後）

1. 空のルームにバックアップを取り込むと、全件が保存される。
2. 同じバックアップをもう一度取り込むと、追加0件・一致して省略N件となる。
3. 既存の半荘IDと一致し内容が異なるデータが1件でも含まれると、他の新規半荘も含めて追加0件となる。
4. 1バッチに重複IDがあればすべて拒否される。
5. 閲覧参加者が `mahjong_import_matches` を直接呼び出しても拒否される。
6. 501件以上のバッチは拒否される。
7. 別ユーザーの非公開ルームの一覧と半荘は閲覧できない。

**このチェックリストは未実施です。** SQLとJavaScriptのファイル作成・構文確認はできましたが、実際のSupabaseプロジェクトでの統合テストは未実施です。

### データ保持の注意

`mahjong_room_matches` と変更履歴は半荘JSONに加えて、プレイヤー登録表、ルール設定、統計除外情報などのバックアップメタデータをJSONBで保存します。クラウド上の両方からv2.22互換形式のJSONを再構成できます。ただし実際のv2.22への再読み込みとSupabaseへの接続はまだ実機検証していません。元バックアップは引き続き保管してください。

## 2026-11-25: v3.0 フルバックアップ基盤

- `mahjong_room_backup_meta`：v2.22の半荘以外の全フィールドを保持。ルーム作成者のみ更新可能、参加者は閲覧可能。
- `mahjong_import_matches(room_id,items,meta)`：同じトランザクションでメタデータと半荘を保存。異なるメタデータがある場合は一切上書きしません。
- `v3/cloud.html`：保存された半荘とメタデータから `matches` / `suspendedMatches` / `active` を再構成してv2.22互換JSONとして書き出します。
- 元の半荘IDが完了・中断・進行中の間で重複していれば書き出しを中止します。
- 開発用JavaScriptの再構成テスト（単一半荘、重複ID、メタデータ欠落）を実施済み。Supabase接続後の統合テストは未実施です。

**仕様上の制限：** 別々のバックアップから差分の半荘を取り込む場合、非半荘情報が一致しなければ安全のため拒否されます。複数端末でプレイヤー・ルール設定を統合する機能は未実装です。

## v2.22とv3.0のローカル移行ブリッジ（2026-11-25）

- v3/cloud.html で「同じドメインのv2.22記録を確認」すると `localStorage.mahjongPrototypeV1` を**読み取るだけ**で移行候補を検査します。v2.22の保存領域への書き込み・削除は行いません。
- 保存データの不整合があれば送信を拒否します。通常データがあるのに壊れているときは予備コピーへ自動切替しません。
- 端末やドメインが違う場合（例：Netlify公開サイトとGitHub Pages試験版）は、元のv2.22で書き出したJSONを選択してください。ブラウザのlocalStorageはオリジンごとに独立しています。
- 取り込みの前に半荘・参加者などの件数を表示し、明示的に最終確認した後に一括RPCを実行します。
- 元の半荘IDが完了・中断・進行中で重複している場合は、移行前検査とサーバーの両方で拒否します。
- JavaScript構文確認、通常の移行データ、重複半荘ID、不正プレイヤーIDの単体テストを実施済み。
- Supabase実環境での認証・RLS・インポート・復元・モバイル端末のテストは未実施です。

**重要：** 自動クラウド同期ではありません。移行ブリッジはローカル記録の一度きりの読み込み補助であり、v2.22の入力をリアルタイムに同期しません。必ず元のバックアップJSONを別途保存してください。
